# Microduck 硬件规格速查

> 一页纸版本。完整推导过程和证据见 [硬件方案逆向.md](硬件方案逆向.md)。
> 所有数据来自 `pollen-robotics/microduck` 的源码、设备树和配置文件 —— **代码即规格书**。

**一句话**：Radxa Zero 3W（RK3566）跑 Armbian + 一条 1 Mbps TTL 串口总线挂 15 个
Dynamixel XL330 + 两块自制板。

---

## 系统框图

```
                ┌──────────────────────────────┐
                │   Radxa Zero 3W (RK3566)     │  65 × 30 mm
                │   Armbian · 内核 6.1.115      │  Pi Zero 形态
                └──┬────────┬─────────┬────────┘
      /dev/ttyS2   │        │ 40-pin  │ MIPI CSI
      1 Mbps TTL   │        │  I2C3   │
    ┌──────────────┘        │ 400kHz  └── IMX219 摄像头（倒装 180°）
    │                       │
    │              ┌────────▼─────────────────┐
    │              │  Pollen RPI Robot HAT    │  65 × 30 mm 自制板
    │              │   ├ TLV320AIC3104  0x18  │  音频 codec
    │              │   ├ BMI088   0x19/0x68   │  焊了但没用
    │              │   └ Stemma J5 → ToF 0x29 │  VL53L5CX/L8CX
    │              │  电池经此板供电            │
    │              └──────────────────────────┘
    │
════╪══════════ Dynamixel 总线 · Protocol V2 · 1 Mbps ══════════
    │
    ├── 15 × XL330   ID 左腿20-24 / 颈头嘴30-34 / 右腿10-14
    └── imu_to_dxl v2 板   ID 200   ← LSM6DSV16X
```

**核心设计**：一条总线搞定一切。IMU 不走 I2C，做成 Dynamixel 从机挂在舵机总线上，
和 15 个舵机在**同一次 `sync_read`** 里读出。电池电压也不用电量计，
直接读舵机报告的自身供电电压。

## 主控

| 项目 | 值 |
|---|---|
| 模块 | **Radxa Zero 3W** —— 市售模块，**不是定制载板** |
| SoC | **RK3566**（4× Cortex-A55 + Mali-G52 + NPU） |
| 尺寸 | 65 × 30 mm，Pi Zero 形态，40 针树莓派兼容排针 |
| 系统 | **Armbian**（Debian 系），vendor 内核 6.1.115 |
| 策略推理 | ONNX Runtime ≥1.23（装 1.28.0），`dlopen` 加载 |
| NPU 推理 | rknn-toolkit2 —— **Armbian 默认关闭**，需刷 overlay 并重启 |

> 依据：设备树 `compatible = "radxa,zero-3w", "rockchip,rk3566"`；
> 全仓库 "radxa" 出现 182 次。

### 为什么传闻说是树莓派

1. 自制板名字**就叫 "RPI Robot HAT"**
2. Pi Zero 形态 + 40 针树莓派兼容排针
3. 摄像头是**树莓派 Camera v2**（IMX219）
4. **原型阶段确实用的树莓派 Zero 2W** —— `robotd.toml` 注释：50 Hz 控制环
   *"is inherited from the prototype, where it was chosen on a Raspberry Pi Zero 2W"*

前身 Open Duck Mini v2 **至今仍用树莓派 Zero 2W**，因为它不做视觉和 WebRTC 推流。

### 为什么必须 Linux SoC 而非 MCU

要同时跑：ONNX 策略推理 @50Hz、720p30 H.264 硬件编码 + WebRTC 推流、
NPU 目标检测、GStreamer 拥塞控制（占 7.6% 一个核）、蓝牙手柄 + 手机 App + WiFi。
**STM32 / ESP32 做不了。**

## 执行器与总线

| 项目 | 值 |
|---|---|
| 电机 | **Dynamixel XL330 × 15**（每个约 18 g） |
| 电气层 | **单线半双工 TTL**（3 线：数据 + VDD + GND），3.3V |
| 协议 | **Dynamixel Protocol V2** |
| 速率 | **1 Mbps**（EEPROM `baud_rate = 3`） |
| 端口 | `/dev/ttyS2` = RK3566 **UART2，M0 pinmux** |
| 挂载设备 | **16 个**：15 舵机 + 1 块 IMU 板 |
| 控制环 | **50 Hz**，一次 `sync_read` 覆盖全部 16 个，寄存器 124–136 |
| Rust 库 | [`rustypot`](https://github.com/pollen-robotics/rustypot) |

> ❗ **不是 RS232，也不是 RS485。** RS485 是差分双线，Dynamixel 的 XM/XH 系列才用。
> XL330 是 TTL 单线半双工。全仓库搜 `rs485|rs232|direction pin` **零命中** ——
> 代码里没有方向控制 GPIO，方向切换由硬件自动方向电路完成（在 HAT 板上）。

### 舵机 ID 分配

```
左腿   20 21 22 23 24    hip_yaw / hip_roll / hip_pitch / knee / ankle
颈头嘴 30 31 32 33 34    neck_pitch / head_pitch / head_yaw / head_roll / mouth
右腿   10 11 12 13 14    （左腿镜像）
IMU 板 200
```

**第 15 个舵机是嘴（ID 34，索引 9）。** 所有策略都是 `obs[1,61] → act[1,14]`，
动作向量**跳过这个索引** —— 嘴由上层逻辑控制，不由策略控制。

### 总线可靠性（官方实测）

| 指标 | 值 | 出处 |
|---|---|---|
| 丢包率 | **约 8 次/分钟 ≈ 0.27%** | *"Measured on a bench robot at ~8 drops a minute"* |
| 官方定性 | *"One dropped Dynamixel transaction is **ordinary**"* | `robotd/src/main.rs` |
| 症状 | 随机小抽搐（丢读导致策略停一拍回 hold 姿态） | 同上 |
| 容错 | `COAST_TICKS = 3` 用上个好样本滑行 60ms | 同上 |
| 容忍上限 | `max_consecutive_errors = 10` | `robotd.toml` |
| 循环稳定性 | `missed=3` / 15022 ticks，保持 50.0 Hz | `roadmap.md` |
| IMU 数据变质 | 有专门的 `StaleImuTracker`，注释写 *"Known to happen"* | `bus.rs` |

总线利用率估算 **约 25%**（约 500 字节/tick ÷ 1 Mbps ÷ 20ms）——
**瓶颈不是带宽，是信号完整性和单点故障**：单端 3.3V 信号、15 个舵机菊花链、
线束穿过动态弯折的颈部、旁边就是电机 PWM 噪声源。

## 两块自制板

### ① `imu_to_dxl` v2 —— 元件极少，最容易自己做

| 项目 | 值 |
|---|---|
| IMU 芯片 | **LSM6DSV16X**（ST 6 轴，带 SFLP 硬件姿态融合块） |
| 接口 | **Dynamixel 总线**（不是 I2C） |
| 总线 ID | **200** |
| 寄存器地址 | **124** |
| 控制环读取 | 12 字节 |
| 完整诊断块 | 20 字节（另含原始加速度、采样计数、状态标志） |

**12 字节块布局**

| 字节 | 内容 |
|---|---|
| `0..6` | gyro x/y/z，`i16` 小端，±500 dps，**17.5 mdps/LSB** |
| `6..12` | SFLP 四元数 x/y/z，**IEEE fp16**；`w = √(1 − x² − y² − z²)` |

**自己做需要**：LSM6DSV16X + 一颗小 MCU 做 Dynamixel V2 从机
（STM32G0/G4、CH32V203、ESP32 均可）+ 半双工 TTL 收发器，供电从总线取。

### ② Pollen RPI Robot HAT —— 可用现成模块替代

65.02 × 30.02 × 0.84 mm（实测自 `elec_rpi_robot_hat_pcb.stl`），插 40 针排针。

| 器件 | I2C 地址 | 说明 |
|---|---|---|
| **TLV320AIC3104** | `0x18` | TI 音频 codec，I2S 数据 + I2C 控制 |
| **BMI088** | `0x19` / `0x68` | **焊了但没用**（注释原文 "dormant"） |
| **ToF** | `0x29` | 不在板上，经 **Stemma J5** 外接 |

- I2C：40 针 **pin 3 / pin 5**（`GPIO1_A0`=SDA，`GPIO1_A1`=SCL），**400 kHz**
- 上拉：**单对 10k，R12/R13**
- 音频时钟：MCLK **12 MHz**，I2S sysclk **12.288 MHz**（256×48kHz）
- 麦克风接 **Mic3R**（单声道右 PGA），其余输入全关
- **机器人内部供电经此板**

## 传感器

| 类型 | 型号 | 接口 | 备注 |
|---|---|---|---|
| IMU | **LSM6DSV16X** | Dynamixel 总线 ID 200 | 芯片内 SFLP 出四元数，主机不跑融合 |
| ToF | **VL53L5CX / VL53L8CX** | I2C `0x29` @ i2c3 | 15 Hz，多区测距 |
| 摄像头 | **IMX219**（树莓派 Camera v2） | MIPI CSI，I2C `0x10` | **倒装，需 rotation 180** |

- 摄像头传感器钉在 1920×1080@30 模式（避开开机默认模式的 21 fps 上限），
  ISP 缩放输出，默认 720p30 @ 2 Mb/s
- 编码走 **Rockchip MPP 硬件编码器** → WebRTC
- HFOV 约 62°

## 电源与电池

| 项目 | 值 |
|---|---|
| 电池 | **索尼 NP-F550 / NP-F970**（L 系列摄像机电池） |
| 配置 | **2S 锂离子**，标称 7.2 V |
| 满电（带载） | **8.2 V** |
| 空（带载） | **6.6 V** |
| 电量计 | **无** |
| ADC | **无** |

> 注释原文：*"There is no fuel gauge and no ADC. The only measurement available is
> what the servos report as their own supply."*

**电压直接通过 Dynamixel 协议读舵机报告的自身供电电压** —— 即"从总线上看到的电池"，
会随负载下沉、静止时回升。所以 6.6–8.2 V 是**带载可用区间**，不是电芯化学量程。

电池 EMA（约 10 秒时间常数）跌到 6.6 V → **自动优雅坐下并关机**。

> 💡 复刻友好：**不需要设计任何电池监测电路。**

| 接口 | 用途 | 参数 |
|---|---|---|
| **UART2** (`ttyS2`) | 15 舵机 + IMU 板 | 1 Mbps，TTL 半双工 |

## 三个必踩的坑

1. **Armbian 默认在 UART2 上跑登录控制台** —— `serial-getty@ttyS2` 的 `agetty`
   会占着串口。必须 `systemctl mask serial-getty@ttyS2`。
   官方是用 `fuser -v /dev/ttyS2` 查出来的。

2. **i2c3 与 FUSB302 抢引脚** —— RK3566 的 i2c3 在原厂 DTB 里跑 M1 pinmux
   服务 USB-C PD 控制器；用 pin 3/5 的 M0 就得禁用 fusb302，**失去 PD 协商**。
   好在 FUSB302 上电默认 CC 呈 Rd，普通 5V 充电仍然可用。

3. **NPU 默认关闭** —— Armbian 出厂不开，跑 rknn 模型要刷 overlay 并重启。

---

## 结论

**这套硬件没有不可复刻的部分。** 主控是市售模块，两块自制板里只有一块真正需要
自己画（且元件极少、协议已完全还原），另一块可用现成模块替代甚至省略。

真正的门槛是**成本**（15 个 XL330 比整机售价还贵），不是技术。
