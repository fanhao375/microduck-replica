# 软件从哪来、我们改了什么、上游仓库里碰到的问题

截至 2026-10-14。鸭子上跑的软件，大部分是 Pollen 官方和 kissqy 的，我们在上面打补丁、改配置，再加一些自己的工具。这一页说清楚三件事：**用了谁的**、**我们改了哪里、改动放在哪、推没推**、**在别人仓库里碰到的问题，处理了没有**。给接手的人和他们的 AI 看。每一项的细节都链接到当天的上机记录或[踩坑记录](../踩坑记录.md)。

| [kissqy/Microduck-kissqy](https://github.com/kissqy/Microduck-kissqy) | **源码公开（Source-available），分项许可**：`firmware/` 下的 Rust 工作区和上游代码（robotd、padd 等）是 Apache-2.0；中控 `firmware/console/`、`firmware/policies/` 里他自训的模型、训练中控、他新写的文档和工具是**个人非商业许可**——公司或组织用途、产品销售、收费服务都要事先取得他的书面许可 | R17 / V164 运行时、中控、联合走路模型、一键镜像 R1、HD-1910 的部署合同 |

**我们跟 kissqy 的约定（我们 10-12 定的）**：
- 不给 kissqy 提 PR。我们的补丁放在自己这边：以他的最新版为底，叠上我们的补丁，跟着他更新；
- 保留他的许可和署名，标明哪些是我们改的，不换名、不商用；
- 他的中控受非商业条款约束，**中控的改动不放进本仓库**。以后做「傻瓜式」页面，自己写引导页去调他的程序和接口，不改他的中控；10-14 起我们通过 fork 维护 robotd 等 Apache 许可部分的改动，当时保留上游中控原样。复刻版本的构建信息见[公开发布页](https://github.com/fanhao375/microduck-replica/releases)；
- 发现他那边的问题可以提 Issue，**提之前先整理好数据，两个人都看过再发**。

## 5. 以后怎么做

最新官方版本、开发分支与 PR 状态集中记在[官方更新跟踪](官方更新跟踪.md)，与下列适配原则一起使用。

- **能用上游现成的就用**，缺什么补什么。自己另写一套运行程序，每个细节都是看不见的变量（踩坑记录「策略训练与真机迁移」第一条）；
- **补丁做小、分支清楚**：每个补丁一个分支，提交说明写为什么，方便跟着上游更新、以后要提 Issue 也能直接附上；
- **先确认参数在哪生效，再改**：同一个名字可能有好几处（toml、模型包、舵机 EEPROM、RAM），改之前先找到「运行时实际在用的值」从哪读；
- **上游有更新时**：先看改了什么、跟我们的补丁冲不冲突，再决定是整体升级还是只移植（[10-13 官方 0.17 的处理](HD1910-20261013-官方更新与UDP手柄.md)）。
