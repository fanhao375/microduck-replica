## 一、先看全局：五个模块，只有两块要自己做

```
                    ┌─────────────────────────────────────────┐
                    │  头（MJCF 里的 jaw_soft 刚体）            │
                    │                                          │
   MIPI CSI ────────┤  ④ IMX219 摄像头 + M12 镜头              │
   （约 13mm，       │        ↕ 同一刚体，中间没有关节           │
    不过脖子）       │  ① Radxa Zero 3W    主控                 │
                    │        ↕ 叠层间距 7.3mm，40 针排针         │
                    │  ② RPI Robot HAT    配电 / 音频 / 总线    │
                    │        └─ Stemma 口 ──► ⑤ ToF 模组        │
                    │  喇叭                                     │
                    └──────────────┬──────────────────────────┘
                                   │
                    ═══════════════╪══════ 穿过三自由度的脖子 ══════
                     舵机总线(1对) │ 电池供电线(+BATT)
                                   │
                    ┌──────────────┴──────────────────────────┐
                    │  躯干（trunk_base）                       │
                    │   两颗 hip_yaw XL330 —— 内腔基本被占满     │
                    │   ③ imu_to_dxl 板（挂在舵机总线上）        │
                    └──────────────┬──────────────────────────┘
                                   │
                     NP-F550 电池 ─┘ 外挂在机身后下方
                     71mm 长有约 40mm 悬在壳体外，
                     由两片 power_support 从外面夹住
```

| # | 模块 | 一句话 | 怎么来 |
|---|---|---|---|
| ① | **Radxa Zero 3W** | 大脑。跑 Linux、神经网络策略、视觉 | 🛒 买 |
| ② | **RPI Robot HAT** | 配电盘 + 音频卡 + 舵机总线接口 | 🏭 **官方开源，自己打样** |
| ③ | **imu_to_dxl** | 把 IMU 伪装成一个假舵机 | ✏️ **要自己画** |
| ④ | **IMX219 摄像头** | 眼睛 | 🛒 买 |
| ⑤ | **ToF 模组** | 8×8 区测距，不是激光雷达 | 🛒 买 |

> ⚠️ **常见误解三连**
> 1. **没有激光雷达。** ToF 是多区测距模组（4×4 或 8×8 区），不是雷达。
> 2. **音频不是独立模组。** codec、功放、麦克风全在 HAT 上。
> 3. **主控不在躯干，在头里。** 这条最容易搞错，直接影响你买多长的排线。

## 二、① 主控 · Radxa Zero 3W

**干什么**：跑 Armbian Linux、跑 Rust 运行时 `robotd`、跑 ONNX 策略推理、跑视觉。
一句话 —— **除了驱动电机，其它都是它干的**。

| 项 | 值 |
|---|---|
| SoC | Rockchip **RK3566**，四核 Cortex-A55 @1.6GHz |
| NPU | 0.8–1 TOPS INT8，节点 `npu@fde40000`，**Armbian 默认关闭**，要上 overlay |
| 形态 | **65 × 30 mm**，树莓派 Zero 形态，40 针排针 |
| 系统 | Armbian **headless** 镜像 |

**为什么是这块板，不是树莓派**：它是**市售模块**，不是定制载板 —— 这一条很重要，
意味着复刻不需要做主控板。设备树里写死 `compatible = "radxa,zero-3w"`。

**它用掉了哪些 40 针引脚**（从官方 HAT 原理图提取）：

| 引脚 | 用途 | Linux 设备 |
|---|---|---|
| **GPIO14 / GPIO15** | **Dynamixel UART Tx / Rx** | `/dev/ttyS2` @ 1 Mbps |
| **GPIO02 / GPIO03** | I²C —— IMU + 音频 + Stemma | `i2c3` @ 400 kHz |
| GPIO18 / 19 / 20 / 21 | 音频 PCM Clk / FS / Din / Dout | `i2s3_2ch` |
| GPIO06 | 关机检测（Switch off detection） | |
| GPIO22 | HAT 上 BMI088 的中断脚（**软件不用**） | |
| GPIO00 / 01 | HAT 身份识别 I²C（保留） | ⚠️ 见 HAT 一节 |
| GPIO04/05、08/09、10/11 | 额外 Stemma/QT I²C | |
| MIPI CSI | 摄像头 | |

**买哪个配置**：2G / 16G eMMC。推算过程见 [电控采购清单](电控采购清单.md#该买哪个配置--按实测体量推算)。
⚠️ **官方实际用哪档配置，全库检索不到任何依据 —— 未知。**

## 三、② RPI Robot HAT —— 一块板干四件事

**这是唯一一块官方完整开源的板**（[`pollen-robotics/elec_RPI_Robot_HAT`](https://github.com/pollen-robotics/elec_RPI_Robot_HAT)，
Apache-2.0，含 KiCad 工程 + Gerber + BOM + 贴片坐标）。

**规格**（Gerber 实测）：4 层板，**65.0 × 30.9 mm**，圆角 R3.5，BOM 47 行 / 123 颗，
其中 5 行 9 颗 DNP，实际贴装 **113 个位置**。

### 功能块 1：配电

```
NP-F550 电池 ──► +BATT ──┬──► 舵机（直供，不降压）
  2S，6.6–8.2V           │
                         └──► U9 AP63205 + L4 6.8µH ──► Q2 / U10 LM5050-1 ──► +5V
                                buck，2A，Fsw 1.1MHz      理想二极管 + 关机检测      │
                                                                                     ├─► 主控 40 针
                                                                                     ├─► PAM8406D 功放
                                                                                     └─► U3 XC6206P182 → +1V8（codec）
```

**这里有个反直觉的事实：舵机吃的是电池原压，不是 5V。**

XL330 的官方额定是 **3.7–6.0 V，推荐 5.0 V**，而这里给它 **6.6–8.2 V**。
证据不是推测，是原理图直接写着：J13/J14/J3/J11 四个 Dynamixel 接口的电源脚全接 `+BATT`，
旁注「3A max」。而**整块板只有一颗 buck（U9）和一个电感（L4）**，那路 5V 是给主控的
—— 2A 的 AP63205 也带不动 15 个 XL330（单个堵转约 1.5A）。

详见 [电压真相](执行器选型.md#-电压真相xl330-被超压运行)。

> `+3V3` 反过来是**主控经 40 针供给 HAT** 的，不是 HAT 自己产生的。

### 功能块 2：舵机总线（半双工 TTL）

Dynamixel / 飞特这类总线舵机都是**单线半双工** —— 一根线上既发又收，靠方向控制切换。

| 器件 | 作用 |
|---|---|
| **U6 `SN74LVC1G125`** | 三态缓冲，发送方向 |
| **U7 `SN74LVC1G126`** | 三态缓冲，接收方向 |
| **U5 `74LVC1G08`** | 与门，参与方向逻辑 |
| **U8 `SIT3088E`** | RS-485 收发器（给 4P 那两个口） |
| **TH1 100R** | 热敏电阻，过流保护 |

方向由 `Dynamixel_dir` 控制，官方注释写着 **「Dynamixel_dir is based on Tx」** —— 从发送信号自动推导方向。

**连接器四个，两种**：

| 位号 | 类型 | 谁用 |
|---|---|---|
| **J13 / J14** | **JST EH 3P**（TTL） | **Microduck 的 XL330 走这两个**，经 TH1 到 `+BATT` |
| J3 / J11 | JST EH 4P（RS-485） | 由 U8 驱动，直接 `+BATT` |

> 💡 **JST EH 是 2.5 mm 间距**，而飞特舵机线材标的是 **5264 端子**，也是 2.5 mm。
> 国内市场上「5264」基本就是 2.5mm 3P 的通称 —— 大概率能直接插，但壳体卡扣细节
> 建议拿实物确认。

### 功能块 3：音频

| 器件 | 作用 | 地址 |
|---|---|---|
| **U2 `TLV320AIC3104`** | 音频 codec，I²S 数据 + I²C 控制 | i2c3 `0x18` |
| **U1 `PAM8406D`** | D 类功放 | |
| **MK1** | 板载 MEMS 麦克风（LCSC `C7587901`，官方未给型号） | |
| J1 | Wago 免螺丝端子，接 **5W 喇叭** | |
| J2 / J9 | Wago 端子，接外置麦克风 | |

音频时钟：MCLK 12 MHz 固定晶振，I²S sysclk 12.288 MHz（256 × 48 kHz）。

> **不要录音和喇叭的话，这一整块可以省掉。**

### 功能块 4：传感器扩展

- **J5–J8**：JST SH 1.0 mm 4P（Qwiic / Stemma QT）—— ToF 就挂在这里
- **U11 `BMI088`**：⚠️ **贴了片，但软件根本不用**。设备树注释原文是 `dormant`、
  `unused but still connected`。外界说 Microduck「有两颗 IMU」指的就是它
- **U4 `CAT24C32`** EEPROM：⚠️ **DNP，不贴** —— 所以这块板**不是自识别 HAT**，
  虽然原理图上写着「HAT Identification: I2C add. 0x50 / Standard Class HAT+」

### 这块板买不到，怎么办

**Pollen 不单卖**，只卖整机。两条路：

1. **忠实打样** —— 拿官方 Gerber + BOM + 贴片坐标去嘉立创下单。4 层板 + SMT，几百元起，有起订量。
2. **用现成模块顶掉** —— ¥22 的 ST/SC 半双工转接板 + 一个 UBEC，就顶掉了「舵机总线」和
   「配电」两件必需功能，ToF 直接挂 i2c3。代价是失去板载音频。见 [电控采购清单](电控采购清单.md#六两块-pcb)。

## 四、③ imu_to_dxl —— 整个电控里最聪明的一笔

**这块板只干一件事：把 IMU 伪装成一个假舵机。**

它是 **STM32G031F8P6 + LSM6DSV16X**（ST 六轴 IMU）+ 半双工缓冲，
对外表现成挂在舵机总线上的一个从机，**ID = 200**。

### 为什么要这么绕

直觉做法是 IMU 走 I²C 或 SPI 直连主控。但那样有个问题：

**IMU 数据和舵机数据是两条不同的路，采样时刻对不齐。**

策略是 50 Hz 跑的，每个 tick 要同时知道「身体姿态」和「15 个关节角度」。
如果 IMU 走 I²C、舵机走 UART，两者之间会有几毫秒的抖动 —— 而抖动会直接污染策略输入。

Pollen 的做法是**让 IMU 也说舵机的语言**，这样主机一个 tick 只发**一次 `sync_read`**，
就同时拿回 IMU 姿态 + 15 个舵机位置，**时间戳天然对齐**。

### 协议与寄存器

| 项 | 值 |
|---|---|
| 协议 | Dynamixel **Protocol V2** |
| ID | **200** |
| 波特率 | **1 Mbps**（EEPROM 寄存器 `baud_rate = 3`） |
| 起始寄存器 | **124** |
| 长度 | **12 字节** |

12 字节的布局：

| 偏移 | 内容 |
|---|---|
| `0..6` | gyro x/y/z，`i16` 小端原始计数，量程 **±500 dps**，**17.5 mdps/LSB** |
| `6..12` | SFLP 四元数 x/y/z，**IEEE 半精度 fp16**；`w = √(1 − x² − y² − z²)` |

**注意 `w` 不传** —— 靠单位四元数的约束在主机侧算回来，省 2 个字节。

**SFLP** 是 LSM6DSV16X 芯片内的**硬件传感器融合块**，直接输出游戏旋转四元数
—— 主机不用自己跑姿态融合。

### 总线上一共 16 个设备

```
ID  10 11 12 13 14   右腿
ID  20 21 22 23 24   左腿
ID  30 31 32 33 34   颈 / 头 / 嘴
ID  200              imu_to_dxl 板
```

15 个舵机 + 1 块 IMU 板 = **16 个设备，一次 `sync_read` 全读回**。

### 复刻时要注意

- **协议和寄存器布局已完整还原**，照着实现即可（[硬件方案逆向](硬件方案逆向.md)）
- **连接器用 2.5 mm 间距 3P**（JST EH / 5264）
- **输入电容耐压 ≥25 V** —— 总线满电 8.4 V，10 V 规格余量不够（MLCC 还有直流偏压衰减）
- **CS 脚要加上拉** —— 见下一节的真实案例
- **DATA 线加 TVS** —— 带电插拔舵机是常态

## 五、④ IMX219 摄像头

MIPI CSI 接口，8 百万像素。设备树 overlay 用的是 `radxa-zero3-rpi-camera-v2`，
ISP 配置 `SENSOR = imx219`。

**两个坑：**

1. **是转 90° 不是倒装 180°。** 代码里写着
   `/// 90, because the head camera is mounted a quarter turn off, and this is the one place
   that fact is written down.` 有些早期资料写 180，那是 **alpha 机**的数据。
2. **排线买最短的。** 摄像头和主控**在同一个刚体里，相距约 13 mm，中间没有关节** ——
   MIPI 线不穿过脖子。4–15 cm 足够，别买 30 cm。

> ⚠️ Radxa 官方文档只写了「1x4-lane MIPI CSI」，**没给引脚数和间距**。
> 但板子是 Pi Zero 形态、CSI 座与 Micro HDMI 同边，**极可能是窄口 22 针 0.5 mm**，
> 而通用 IMX219 模组配的是标准 15 针 —— 备一根转接线（几块钱）。

## 六、⑤ ToF 模组

**不是激光雷达。** 是 ST FlightSense 的多区测距芯片，输出一个 **8×8 的距离矩阵**。

| 项 | 值 |
|---|---|
| 型号 | **VL53L5CX 或 VL53L8CX**，固件按 revision ID 自动识别（`0x02` = L5cx，`0x0C` = L8cx） |
| 接口 | I²C，挂在 **i2c3 @ 400 kHz** |
| 地址 | **`0x29` 或 `0x52`**（两个候选都试） |
| 物理连接 | HAT 上的 **JST SH 1.0 mm 4P**（Qwiic / Stemma QT） |
| 帧率 | 15 Hz |

> ⚠️ **别买成 VL53L0X** —— 那是**单点**测距，固件不认。
> **VL53L7CX 也不是 L8CX**（L7 是 90° 视场的另一颗）。

## 七、一个 tick 里发生了什么

策略 50 Hz 跑，也就是 **每 20 ms 一轮**：

```
   ① 一次 sync_read                 ttyS2 @ 1 Mbps
      ├─ ID 200  → gyro + 四元数     ┐
      ├─ ID 10~14 → 右腿 5 个角度     ├ 12 字节 × 16 设备
      ├─ ID 20~24 → 左腿 5 个角度     │  时间戳天然对齐
      └─ ID 30~34 → 颈/头/嘴 5 个     ┘

   ② 组装 61 维观测向量

   ③ ONNX 策略推理（775 KiB 的小网络）→ 14 维动作

   ④ 电压自适应：scale × (7.4 / 实测电池电压 EMA)
      —— 电池从 8.4V 掉到 6.5V，同样的 PWM 力矩差很多，不补偿策略会飘

   ⑤ 一次 sync_write，把 14 个目标位置发下去
```

旁路上还跑着：**i2c3** 上的 ToF（15 Hz）和音频 codec、**MIPI CSI** 上的摄像头。

> ⚠️ **20 ms 预算很紧，而且不只是飞特的问题。**
> 官方源码里写着：XL330 出厂 `return_delay_time = 250`，即 **每个设备 500 µs 的转向延迟**，
> 「Across 16 devices that is **8 ms per tick — 40% of a 20 ms budget**」。
> 官方的解法是把这个寄存器**写 0**。
> 换任何舵机，这一步都要重做并实测。

## 八、走飞特路线，哪些会变

很多人（包括本仓库）在评估用飞特舵机替代 XL330。影响按严重程度排：

| 影响 | 说明 |
|---|---|
| 🔴 **官方 9 个 ONNX 策略大概率失效** | 舵机换了，力矩曲线、质量、可能连减速比都不同。**必须重训**（需要 CUDA GPU 或 HF jobs） |
| 🟡 **总线时序必须实测** | 飞特走 Protocol V1，包格式不同。**但不要假定它一定更慢** —— 官方 Dynamixel 路径同样有每设备转向延迟（见上）。到货第一件事是跑基准测试，配一块 **FE-URT-1 调试板** |
| 🟡 **`imu_to_dxl` 要重新定位** | 总线协议变了，这块板要么改成模拟飞特从机，要么放弃"挂总线"设计让 IMU 走 SPI 直连。**建议：硬件不变、固件双协议** —— 两者物理层完全相同（半双工单线 TTL / 1 Mbps / 3 线），差别只在包格式（V2 是 `FF FF FD 00` + CRC-16，飞特是 `FF FF` + `~sum`） |
| 🟢 **电压反而更合适** | 飞特 HD-1910 原生 5–8.4 V，不用像 XL330 那样超压运行 |

## 九、怎么自己核对：复刻前必做的五件事

**这一节比上面所有内容都重要。**

开源项目的资料会过时、会有错，AI 生成的原理图更是如此。下面是本仓库在实践中
总结出的核对动作 —— 每一条都对应一次真实的翻车。

### 1. 引脚定义：翻数据手册的引脚表，一个一个对

**真实案例：** 本仓库收到过一个 `imu_to_dxl` 的原理图 PR。图画得很完整，但把
LSM6DSV16X 的引脚接错了 —— 核对 **ST DS13510 Rev 1 Table 1**（第 10 页）发现：

| 脚 | 手册定义 | PR 里画的 |
|---|---|---|
| **12** | **CS**（片选） | ❌ 错位 |
| **13** | **SCL**（SPI 时钟） | ❌ 错位 |
| **14** | **SDA**（SPI 数据） | ❌ 错位 |
| **2 / 3** | **SDx / SCx 辅助接口**，不用时手册要求**接 GND** | ❌ 当成主接口 |

这块板做出来是**不工作**的。而发现它只需要一件事：**打开手册，翻到引脚表，逐行对**。

> **画原理图不看手册，等于没画。** 这句话没有例外。

### 2. 电压余量：每个电容的耐压 vs 实际总线电压

同一个 PR 里，输入电容标的是 **10 V**，而总线满电 **8.4 V**。看似有余量，但：
- MLCC 有**直流偏压效应**，8.4 V 加在 10 V 规格的 MLCC 上，实际容量可能掉一半以上
- 电池、电机反电动势会有尖峰

**规则：耐压至少是工作电压的 2 倍。** 8.4 V 的总线，用 25 V。

### 3. 上电状态：模式选择脚在上电瞬间是什么电平

LSM6DSV16X 的 CS 脚电平**在上电时决定走 SPI 还是 I²C**。如果 CS 悬空，
上电瞬间是不确定的 —— 有时能跑，有时不能，最难查的那种 bug。

**加一个 10 kΩ 上拉到 3V3**，锁定 SPI 模式。

### 4. 跑 ERC，而且要跑到 0 错 0 警告

KiCad 命令行就能跑：

```bash
kicad-cli sch erc --output erc.rpt your.kicad_sch
```

常见的真问题：电源脚没有驱动源（缺 `PWR_FLAG`）、两个 Power output 撞在一起、
引脚坐标不在连接栅格上（看着连上了其实没连）。

### 5. 交叉验证：软件源码里的地址和寄存器 vs 硬件

Microduck 的软件是开源的，**代码即规格书**。硬件上的每一个地址都能在代码里找到对应：

| 硬件 | 软件里的证据 |
|---|---|
| 音频 codec `0x18` | `deploy/audio/i2c3-pihat.dts` |
| ToF `0x29` / `0x52` | `tof/src/main.rs` 的 `ADDRESS_CANDIDATES` |
| IMU 板 ID 200 | `duck-control/src/model.rs` 的 `IMU_DXL_ID` |
| 舵机 ID 分配 | 同上，`JOINT_IDS` |
| i2c3 400 kHz | `i2c3-pihat.dts` 的 `clock-frequency` |
| BMI088 没用 | `i2c3-pihat.dts` 注释：`dormant`、`unused but still connected` |

**对不上就是有一边错了。**
