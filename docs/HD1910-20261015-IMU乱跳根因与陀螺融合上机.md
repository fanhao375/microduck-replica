# 2026-10-15 · 「走两三步就摔」的根因：BNO085 姿态乱跳；陀螺融合上机后能稳定走

**机器**：第一台，新卡（kissqy V167 / control.43 + 我们 fork 的 I²C IMU），BNO085 模块胶粘在机身里，接主板 I2C4（0x4B）；舵机全默认（P = 5、D = 0、转矩限制 1000，不设参数文件）；联合 Walk 模型动作缩放 0.9、头滤波 0.5、腿滤波 0.7；全硅胶脚底；整鸭带电池 **806 g**（kissqy 训练用 820 g）。
**前情**：10-12 夜 IMU 装歪的问题修好后，鸭子能站、会迈步，但从 10-12 到 10-14 一直是「推摇杆走两三步就摔」。中间试过换脚底、调舵机 D、调滤波和缩放、对仿真，都没解决（见 [10-13 夜](HD1910-20261013-夜-掉电-舵机D与蹭地.md)、[10-14 白天](HD1910-20261014-白天-仿真找原因与新版放开参数.md)）。

**一句话结论**：
1. **根因**：BNO085 芯片**自己算的姿态**（游戏旋转向量）在走路时（发作起点约一半在落脚前后）会在 20 ms 里跳 20～60°，同一时刻芯片的陀螺说机身几乎没转。模型看到的重力方向跟着跳，等于突然被告知「你在倒」，它一纠正就真倒了。芯片的陀螺本身是好的。
2. **解决**（纯软件，不换传感器）：robotd 里用芯片的陀螺自己积分出姿态，每来一个芯片姿态就比一下，差得少就慢慢跟，差得多就不信。配置项 `[trunk_imu] bno08x_fusion = "gyro"`。
3. **上机结果**（10-15 晚，实测）：
   - 原来的模式（`chip`）：在 walk 模式里直立 62 s（其中推摇杆 9 s），摔 3 次；
   - 新模式（`gyro`）：在 walk 模式里直立 634 s（其中推摇杆 60 s，其余是站着、踏步），推着摇杆的时候一次没摔，全程只摔 1 次（两次推杆之间）；
   - 同一段时间芯片照样乱跳 745 次，模型那一路没跟着跳。模型看到的姿态里只有 1 次超过 5°（7.2°），是 IMU 数据停了约 0.1 s、恢复时一帧追上来，不是融合跳（§5.4）。

   用户在现场的判断是「chip 疯狂摔，gyro 基本不摔、非常稳」，**决定不再做轮流对比，直接用 gyro**。所以这里**没有**完整的 A/B 统计，只有上面两段录像和现场观察。
4. **还没解决的**：转向很弱（原地转只有指令的四分之一左右）；19:31 板子整机重启了一次（现象跟 10-13 一样，没有关机过程；掉电还是死机没定）；融合的门限还没用今晚的 100 Hz 数据重新定。

## 1. 现象：走两三步就摔（10-12 ～ 10-14）

- 模型接管、站着都稳；一推摇杆，迈两三步就往前或往侧面扑倒。
- 换过胶布、TPU、橡胶、硅胶四种脚底：越抓地越容易摔。胶布、TPU 时其实是在打滑，没真正走起来；硅胶不打滑以后问题才完全暴露。
- 舵机越硬（D 越大）越容易摔。
- 10-14 我们一度以为是「膝盖只摆 1/3、舵机跟不上」，打算重训模型。

## 2. 排查策略

### 2.1 跟跑通的人逐条对差别

群里有人用**同样的 HD-1910 舵机、同样的 kissqy 模型**跑通了。我们问了他的舵机参数，回答是「P5 D0，其他都是默认的」，也就是 V167 不设参数文件时的状态。所以舵机和模型本身没问题，问题在我们跟他的差别上。我们把差别列出来，一条一条排：

| 差别 | 怎么排 | 结果 |
|---|---|---|
| 舵机参数 | 改成跟他一样：不设参数文件（P5 / D0 / 1000），缩放 0.9、头 0.5、腿 0.7 | 今晚就是这套，chip 模式照样摔 |
| 重量 | 称整鸭 | 806 g，训练用 820 g，差 1.7%，排除 |
| **IMU 芯片** | 我们是 BNO085；kissqy 的一键镜像只认他的总线 IMU 小板（ST 的 LSM6DSV16X），**推断**跑通的人用的是 ST 芯片（没当面问过） | **头号嫌疑，见 §3** |
| 电源 | 10 A 可调电源 10-16 到 | 还没排 |
| 脚底 | 他的是什么材料没问 | 还没排 |
| 机械 | — | 还没排 |

### 2.2 先找「物理上不可能」的数据，再调参

10-12 到 10-14 我们调了很多参数，每次都是「好像好一点又好像没有」。10-15 换了个做法：不调参，先检查传感器数据**自己跟自己对不对得上**。

判据很简单：IMU 同时给姿态（重力方向）和陀螺（角速度）。用这一帧的陀螺把上一帧的重力方向往前推 20 ms，应该跟这一帧的重力方向差不多（`dg/dt = −ω × g`）。差 5° 以上，就是「陀螺说没怎么转，姿态却跳了」，物理上不可能，一定有一个在撒谎。

### 2.3 我们走过的弯路（更正记录）

- **「IMU 比关节晚 54 / 64 ms」是错算**（10-14 夜）：用错了 MJCF 里脚的坐标轴，已撤回。
- **「硅胶脚底会绊脚」是错的**（10-14 夜）：用户纠正了。胶布、TPU 时其实是打滑，硅胶不打滑以后，暴露出来的正是 IMU 乱跳（冲击更硬）。
- **「舵机不行，要重训」收回**（10-15）：用户指出「大家好多用他的跑通了」，舵机和模型本身没问题。「膝盖只摆一半」确实存在（见 §6.1），但不是「走两三步就摔」的主因。

## 3. 分析：BNO085 自己算的姿态在落脚时乱跳

### 3.1 结果（10-15 上午，旧卡和新卡的录像，约 60 万帧，50 Hz）

- **走路时芯片姿态成段乱跳**：20 ms 内倾斜跳 20～60°，同一时刻陀螺只转了 1～2°。53 次发作的起点里，约一半在换脚前后 60 ms 内。
- **乱跳比例跟脚底、舵机硬度有关**（推摇杆走路的帧里）：

  | 条件 | 乱跳帧比例 |
  |---|---|
  | 胶布脚 | 1.9% |
  | 硅胶，P3 / D0 | 4.9% |
  | 橡胶 | 8.8% |
  | 硅胶，P5 / D4 | 23.2% |
  | 硅胶，P5 / D0（10-15 晚新卡，chip 模式） | 31.7%（只有 546 帧，样本小） |
  | HOME 静站 | 0.05% |

- **起步后中位 1.8 s 第一次发作**，正好是「走两三步」。
- **跟摔倒对得上**：走路中的摔倒约八成，摔前 1.5 s 内有乱跳。10-15 晚 chip 模式的 3 次摔倒，3 次摔前 1.5 s 内都有。这一条没有基线（推摇杆时乱跳本来就占三成，随便取 1.5 s 也常有），只作参考；更有分量的是下一条和 §5.4。
- **策略被误导的程度**：发作 0.6 s 内，模型看到的重力方向偏离陀螺积分，段内最大值中位 31°（90% 分位 62°）；不发作的走路对照只有 0.8°。

### 3.2 排除了什么

| 怀疑 | 怎么排的 | 结论 |
|---|---|---|
| I²C 读坏了 | 跳的那些帧，四元数原始值（Q14）的长度正常（中位 16384） | 不是读坏，是芯片自己融合出来的 |
| 陀螺也不可信 | 陀螺跟四元数求导的角速度逐轴相关 0.97～0.99，比例 1.00～1.06；腿的正运动学站在陀螺一边 | 陀螺可信 |
| 装歪、坐标系、单位 | 倾斜测试：前后倾只有俯仰变、左右歪只有横滚变，偏航安装误差约 −1.7° ± 2° | 没问题 |
| 模块松动 | 用户确认胶粘得很牢，一点不动 | 不是松动 |
| 线加速度造成的 | 偏差跟线加速度的相关约 0 | 解释不了 |

### 3.3 机理（推测）

芯片内部用加速度计校正倾斜。脚落地的冲击很硬，加速度计读数在几毫秒里乱掉，芯片的融合算法就跟着把姿态拉偏。脚越抓地、舵机越硬，冲击越大，乱跳越多，跟 §3.1 的表一致。芯片内部怎么算的我们看不到，**这一条是推测**，但修法不依赖它：只要陀螺可信，就可以不信芯片的姿态。

## 4. 解决：robotd 里用芯片的陀螺自己积分姿态

### 4.1 为什么只改软件

用户要求传感器不换，只改软件。备选也记一下：想对照 ST 芯片，可以在躯干上另接一块 LSM6DSV16X 模块（fork 支持 `source = "lsm6dsv16x"`，还没上过真机）。官方 HAT D1 版板载的那颗 LSM6DSV16X 在 J5（I2C3）上，HAT 装在头里，只能当头部 IMU，不能代替躯干 IMU；我们的 BNO085 接的是 I2C4。

### 4.2 算法（审核后的最小版）

当时的实现记录在 `hd1910-v167-gyro-fusion` 的 `robotd-design.md` §2.6。流程如下。

- 芯片每 10 ms 报一次陀螺，robotd 拿它积分出一份自己的姿态；
- 芯片每报一次姿态，就比一下两份姿态的倾斜差 θ：
  - **θ < 6°**：相信芯片，按时间常数 0.66 s 慢慢跟过去；
  - **θ ≥ 6°**：不信芯片，这一下靠陀螺撑着；
  - **连续不信 0.5 s**：芯片自己平稳、机身也静止（比如摔倒后躺着）→ 一步对齐到芯片；还在动 → 按每秒不超过 5° 的速度往芯片那边拉，不会突然跳；
- 只管倾斜，航向不设门限；
- 时间一律用报告序号 × 10 ms，不用主机时间（主机一次读到一串积压的报告，它们之间仍然是 10 ms）；
- 陀螺断档（序号跳太多，或主机时间隔了 100 ms 以上）后，等芯片平稳 0.5 s 再整步对齐。

### 4.3 怎么保证不出事

- **默认 `chip`**：装上什么都不改，发给模型的姿态跟以前一个字段都不差（有随机包差分测试钉住），融合只在后台陪跑、出诊断。这叫**影子模式**。
- **`gyro` 要自己切**，用 IMU-MODULE.md 4.4 节的命令（板上 kissqy 自己的 `configure.py` 写，**别用 nano、sed 手加**：同一节写出两行同名键，所有版本的 robotd 都起不来）。
- **融合内部出错**：panic 被接住，融合关掉（`disabled`），自动退回发芯片姿态。
- **原始日志**：`bno08x_raw_log` 把芯片每一条报告写进 CSV，64 MB 封顶，写盘跟不上就丢行计数，不拖慢 IMU。
- **停止规则**：上机每一步都有「看到什么就退回 chip」的规则（§5.5）。
- **撤回**：安装脚本自动备份，`rollback <备份目录>` 一条命令回到安装前。

### 4.4 过程（每一步都先定方案、审核，再动手）

1. **方案**：先只出方案，用 50 Hz 录像离线回放 Python 参考实现，比较几种门限和追的方式。早期原型（门限 4°）的回放：发散段的乱跳从 72 次降到 0，静站与芯片差中位 0.08°。
2. **方案审核**：独立审核砍成最小版，见 §4.2。最小版在同一批录像上回放：直立走路中台阶 0 次（4 次都在倒地之后），HOME 静站与芯片差中位 0.011°。
3. **实施**：Rust 纯核心 + 接进 BNO08x 读取 + 配置项 + 诊断 + 原始日志 + 安装脚本保留新键 + 文档，10 个提交。
4. **两轮代码审核**，必须改的两条：
   - 写键用 sed 跑两次会产生重复键，所有版本的 robotd 都会在启动第 1 步退出 → 改成用 `configure.py` 写，执行几次结果都一样；
   - 回放里的 4 次「台阶」都在倒地之后 → 停止规则只数直立走路的帧。
5. **测试**：Rust 673 过 / 17 败，失败名单跟没改的基线完全一样；假板子安装测试 73/73；4 段录像回放测试，Rust 跟 Python 逐个相等。

### 5.1 准备

只读摸底 → 备份（板上打包，拉回电脑核对 sha）→ 上传 9 个文件，逐个核对 sha → 安装脚本先 `check` 再 `install`。安装脚本在真板上第一次跑这一版，一次通过。核对：robotd 启动日志里 `bno08x_fusion="chip"`，计数 `mode=chip`、`disabled=false`。

|---|---|

### 5.3 gyro 静站和倾斜

切 `gyro` 后静站 455 s（46 个 10 s 窗口）：最差的一个窗口，融合与芯片倾斜差中位 0.026°、P90 0.096°（停止规则是 0.5° / 1°）；没有一次拒绝、对齐或出错。倾斜测试：后仰时姿态变化 16.7°、陀螺积分 16.7°，回正 −18.0° 对 −17.7°。

### 5.4 gyro 走路

| | chip（影子段） | gyro |
|---|---|---|
| 在 walk 模式里直立的时间 | 62 s | 634 s（推摇杆以外是站着、踏步） |
| 推摇杆时间 | 9 s | 60 s（往前推 13 次，有时斜推，每次 1～8 s） |
| 摔倒 | 3 次（推着摇杆的 2 次） | 1 次（不在推杆时） |
| 芯片那一路 >5° 跳变 | 330 次（这就是模型看到的） | 745 次，全被融合挡住 |
| 模型看到的 >5° 跳变 | 330 次 | 1 次（7.2°）：IMU 数据停了约 0.1 s（陀螺和姿态连着 3～4 帧没更新），恢复时一帧追上来；前后的融合判定都是 accepted，不是融合跳，跟已知的「IMU 过期帧」有关 |
| 融合判定（直立走路帧） | — | 接受 29484、拒绝 2228、追 13，对齐和出错 0 |

按推杆时间算，chip 每分钟摔约 14 次，gyro 是 0。两段不是轮流做的，chip 那段也很短，**这不是 A/B 的结论**（`ab_blocks.py` 会算出 p = 0.016，但它的前提是两段可比，这里不成立，不当结论）。用户现场看了，决定不再比、直接用 gyro。

### 5.5 停止规则：判跳变的尺子在摔倒时会误报

**现象**：chip 影子段里，按原来的口径算，融合那一路有 5 次超过 5°：4 次在摔倒前 0.5 s 内，1 次在推杆刚停、机身晃得厉害时。按 gyro 模式的发布路模拟（发布值也过中值、配本帧陀螺，延迟对齐）是 0 次，但最大 3.75°，离 5° 只差 1.25°，而且都在摔倒那一下。原来「1 次就退回 chip」的规则，随时可能被摔倒本身触发。

**原因**（独立审核复核）：录像里的 `imu.gyro` 过了三点中值，比实际晚一帧；`imu.fusion.fused` 没过中值。拿晚一帧的角速度去外推没延迟的姿态，身体转得快（摔倒时每秒 130～640°）就会差出 5°。5 次都发生在融合「拒绝」的帧里，这种帧融合只做积分，不可能整步跳；融合四元数两帧间的转角跟 100 Hz 原始陀螺的积分对得上（差一条报告的对齐以内）。外推改用下一帧的陀螺，就是 0 次。

**改后的规则**（审核过）：
- 每次跳变看前后 ±2 帧的融合判定：
  - 有 `realign_long`、`realign_gap`、`fallback` 或 `follow`（融合能整步跳的只有这四种）→ **1 次就退回**，不受任何豁免；
  - 只有 `accepted`、`rejected`、`slew` → 摔倒前 1 s 内、或上一帧倾斜已经 ≥30° 的不算；其余每段 ≥3 次退回，1～2 次记下来逐个看。
- IMU 读取卡一下（几帧不更新、恢复时一帧追上）也会算成软台阶，gyro 走路那 1 次就是这样；块长了可能凑够 3 次，到时逐个看是不是卡顿。
- 判据脚本：[`tools/radxa/onboard-analysis/judge_block.py`](../tools/radxa/onboard-analysis/judge_block.py)；分段数摔倒、算每分钟摔几次：[`ab_blocks.py`](../tools/radxa/onboard-analysis/ab_blocks.py)。

### 6.1 转向弱：关节只跟到一半（推断跟 IMU 无关）

| 动作 | 给的转速 | 实际转速 |
|---|---|---|
| 原地右转 | 58°/s | 15°/s |
| 原地左转 | 84°/s | 19°/s |
| 边走边转（3 段） | 61～79°/s | −4～11°/s，有一次转反了 |
| 后退带转（1.2 s） | −79°/s | −43°/s（样本小） |

模型给的目标和舵机实际转到的比（关节角标准差之比，只取摇杆非零的直立帧）：髋偏航 57～95%，髋横滚 31～56%，膝 48～55%，髋俯仰 45～67%。腿只摆出一半，脚抬不起来，没法在空中把脚转过去；全硅胶脚抓地牢，贴地也拧不动（**推测**）。推断这就是以前说的「膝盖只摆一半」，以前被 IMU 乱跳盖住了。转向只在 gyro 模式、重启之后测过，chip 模式没测；按代码，转向用的角速度在两种模式下都是芯片陀螺原值，所以**推断**跟这次的改动无关。

下一步一次只改一样：先问跑通的群友转向灵不灵、脚底什么材料；再试动作缩放 0.9 → 1.0；再试舵机 P 5 → 6、7；10 A 电源到了再比。

### 6.2 整机重启（19:31:42）

鸭子在 walk 模式下原地站着，日志突然断掉，没有关机过程，录像文件末尾是一串空字节，属于掉电或死机。前一刻电池 7.59 V、CPU 78°C、WiFi 正常。跟 [10-13 夜](HD1910-20261013-夜-掉电-舵机D与蹭地.md)「整机重启」是同一类。robotd 是普通进程，崩了也只会自己重启，不会让整块板重启，所以**推断**跟这次的改动无关。但当时原始日志在持续写卡、CPU 78°C，这两点跟 10-13 不同，没排除。原因没定，10 A 电源到了做对照。

## 7. 照着做（用 BNO085 模块的）

1. 按[复刻镜像上手指南](../software/image/烧录和第一次使用.md)接线和确认 IMU 方向。复现本文实验需使用当时的 `hd1910-v167-gyro-fusion` 构建。
2. 先在默认的 `chip` 下站、走，录像（[`duck_rec.py`](../tools/radxa/onboard-analysis/duck_rec.py)），用 `judge_block.py` 看芯片那一路跳多少。
3. 用 4.4 节的命令切 `gyro`，`reconnect`（会卸力，扶住），静站 5 分钟看 θ，再走。
4. 每段前后看一次计数（4.4 节的命令），按 §5.5 的规则判断要不要退回 `chip`。

## 8. 给后来人和 AI 的要点

- **先查数据自己对不对得上，再调参。** 这次最关键的一步，是用「陀螺推出来的姿态 vs 芯片给的姿态」找到了物理上不可能的跳变。之前三天调参都在跟一个被骗的模型较劲。
- **跟跑通的人逐条对差别。** 同样的舵机、模型、参数，别人能走，问题就在差别里。
- **影子模式先行**：新算法先只陪跑、不发布，拿真机数据确认没问题再切。
- **判据也会骗人**：判跳变的尺子要跟数据的延迟对齐（录像里的陀螺过了三点中值、晚一帧）。
- **记录更正**：错的结论（「IMU 晚 54 ms」「硅胶绊脚」「舵机不行要重训」）都留着更正记录，别删。
