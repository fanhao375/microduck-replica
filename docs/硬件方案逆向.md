# Microduck 硬件方案逆向

**方法**：官方开源了 Rust 运行时，而运行时要驱动真实硬件，就必须写死设备路径、
I2C 地址、寄存器偏移、波特率和协议。**代码即规格书**。
本文所有结论都来自 `pollen-robotics/microduck` 仓库的源码、设备树和配置文件。

---

## 一、整体架构

```
                    ┌──────────────────────────────┐
                    │   Radxa Zero 3W (RK3566)     │  65 × 30 mm
                    │   Armbian / 内核 6.1.115      │  Pi Zero 形态
                    └──┬────────┬─────────┬────────┘
          /dev/ttyS2   │        │ 40-pin  │ MIPI CSI
          1 Mbps UART  │        │         │
        ┌──────────────┘        │         └── IMX219 摄像头（倒装）
        │                       │
        │              ┌────────▼─────────────────┐
        │              │  Pollen RPI Robot HAT    │  65 × 30 mm 自制板
        │              │  i2c3 @ 400kHz           │
        │              │   ├ TLV320AIC3104  0x18  │ 音频 codec
        │              │   ├ BMI088   0x19/0x68   │ 焊了但没用
        │              │   └ Stemma J5 → ToF 0x29 │
        │              │  电池经此板供电            │
        │              └──────────────────────────┘
        │
   ═════╪═══════════ Dynamixel 总线 (Protocol V2, 1 Mbps) ═══════════
        │
        ├── 15 × Dynamixel XL330    ID: 左腿20-24 / 颈头嘴30-34 / 右腿10-14
        └── imu_to_dxl v2 板         ID: 200      ← 第二块自制板
              └ LSM6DSV16X
```

**核心设计思想**：**一条 Dynamixel 总线搞定一切**。IMU 不走 I2C，而是做成 Dynamixel
从机挂在舵机总线上，和舵机在**同一次 `sync_read` 事务**里被读出来。
电池电压也不用电量计——直接读舵机报告的自身供电电压。

## 三、自制板 1：`imu_to_dxl` v2

**最巧妙的设计，也是最容易自己复刻的一块。**

| 项目 | 值 |
|---|---|
| IMU 芯片 | **LSM6DSV16X**（ST 6 轴，带 SFLP 硬件传感器融合块） |
| 接口 | **Dynamixel 总线**（不是 I2C！） |
| 总线 ID | **200** |
| 寄存器地址 | **124** |
| 控制环读取 | 12 字节 |
| 完整诊断块 | 20 字节（另含原始加速度、采样计数、状态标志） |

### 12 字节块布局

| 字节 | 内容 |
|---|---|
| `0..6` | gyro x/y/z，`i16` 小端原始计数，量程 **±500 dps**，**17.5 mdps/LSB** |
| `6..12` | SFLP 四元数 x/y/z，**IEEE 半精度 (fp16)**；`w = √(1 − x² − y² − z²)` |

### 为什么这么设计

1. **不占用额外总线** —— 和 15 个舵机在同一次 `sync_read` 里读回，零额外开销
2. **主机不用跑姿态融合** —— LSM6DSV16X 的 SFLP 块在芯片内直接输出游戏旋转四元数，
   还自己估计陀螺零偏
3. **只传 w 的三个分量** —— 单位四元数省一个字节对，12 字节刚好塞进一次事务

### 自己做这块板要什么

- LSM6DSV16X（或引脚兼容的 ST 6 轴）
- 一颗小 MCU 做 Dynamixel Protocol V2 从机（STM32G0 / CH32V 之类足够）
- 半双工 TTL 收发器（Dynamixel 总线是单线半双工）
- 供电从总线取

**这是整个项目里最值得自己画的一块板**，元件少、逻辑清晰、协议公开。

## 四、自制板 2：Pollen RPI Robot HAT

65 × 30 mm，Pi Zero 形态，插 Radxa 的 40 针排针
（对应 STL `elec_rpi_robot_hat_pcb.stl`，实测 65.02 × 30.02 × 0.84 mm）。

### 板载器件

| 器件 | I2C 地址 | 说明 |
|---|---|---|
| **TLV320AIC3104** | `0x18` | TI 音频 codec，I2S 数据 + I2C 控制 |
| **BMI088** | `0x19` / `0x68` | **焊了但没用**（注释原文 "dormant"、"unused but still connected"） |
| **ToF** | `0x29` | 不在板上，通过 **Stemma J5 接口**外接 |

- I2C 总线：40 针的 **pin 3 / pin 5**（`GPIO1_A0` = SDA，`GPIO1_A1` = SCL）
- 总线速率 **400 kHz**（受限于 codec 和 BMI088；VL53L5CX 本可以跑 1 MHz）
- 上拉：**单对 10k，R12/R13**
- 音频时钟：MCLK **12 MHz** 固定晶振，I2S sysclk **12.288 MHz**（256 × 48kHz）
- **机器人内部供电经此板**（电池 → HAT → 主控）

### ⚠️ 一个他们自己踩过的坑（注释里写得很清楚）

RK3566 的 `i2c3` 控制器在原厂 DTB 里跑在 **M1 pinmux**（`GPIO3_B5/B6`，靠近 USB-C 口），
服务 **FUSB302 USB-C PD 控制器**。而 HAT 要用的 pin 3/5 正好是 `i2c3` 的 **M0 pinmux**。

他们的 overlay 把控制器重新 mux 到 M0，并禁用 fusb302 节点。后果：

- **失去 USB-C PD 协商**
- 但 FUSB302 上电默认在两条 CC 线上呈现 Rd（`SWITCHES0 = PDWN1|PDWN2`），
  所以 USB-C 充电器（无论 PD 还是普通）**仍然给 5V** —— 板子本来就只要 5V
- 机器人内部供电走电池经 HAT，与此无关
- maskrom 刷机是 ROM code，不受影响

> 早期版本用的是 **bit-bang I2C**（`i2c-gpio-pihat`），CPU 占用高。
> 改成硬件 I2C 后才让 **15 Hz 的 ToF 流**变得可负担。
> 两种模式互斥，`install.sh` 通过 `MICRODUCK_I2C_MODE=hw|bitbang` 选择。

### 稳定设备节点

`/dev/i2c-3` 通过 udev 规则软链为 **`/dev/i2c-pihat`**，两种模式下消费者代码不用改。

| 项目 | 值 |
|---|---|
| 电机 | **Dynamixel XL330 × 15** |
| 协议 | **Dynamixel Protocol V2** |
| 波特率 | **1 Mbps**（寄存器 `baud_rate = 3`） |
| 串口 | `/dev/ttyS2` |
| Rust 库 | [`rustypot`](https://github.com/pollen-robotics/rustypot)（Pollen 自家的） |
| 控制环 | **50 Hz** |

### ID 分配

```
左腿   20  21  22  23  24     hip_yaw / hip_roll / hip_pitch / knee / ankle
颈头嘴 30  31  32  33  34     neck_pitch / head_pitch / head_yaw / head_roll / mouth
右腿   10  11  12  13  14     （左腿的镜像）
```

> 不由策略控制。
>
> 这套 ID 分配和 **Open Duck Mini v2 完全一致**（20-24 / 30-33 / 10-14），
> 只是多了一个 34。血统印证。

## 五之二、通讯方案（逐条确认）

### 主总线：单线半双工 TTL UART —— **不是 RS232，也不是 RS485**

| 项目 | 值 | 依据 |
|---|---|---|
| 电气层 | **3 线 TTL 半双工**（数据线 + VDD + GND） | XL330 产品规格：3-pin JST，TTL |
| 逻辑电平 | **3.3 V** | RK3566 IO 电平 |
| 协议 | **Dynamixel Protocol V2** | `.with_protocol_v2()` |
| 速率 | **1 Mbps** | `BAUD_RATE = 1_000_000`，EEPROM 寄存器 `baud_rate = 3` |
| 端口 | `/dev/ttyS2` = RK3566 **UART2，M0 pinmux** | `robotd.toml`，`uart2-m0` overlay |
| 挂载设备 | **16 个**：15 舵机 + 1 块 IMU 板 | `ids = [200, 20..24, 30..34, 10..14]` |
| 单次事务 | 一个 `sync_read` 覆盖全部 16 个设备，寄存器 **124–136** | `bus.rs` |

> ❗ **不是 RS485**。RS485 是差分双线，Dynamixel 的 XM/XH 系列才用（4-pin）。
> XL330 是 **TTL 单线半双工**（3-pin）。全仓库搜 `rs485|rs232|half-duplex|direction pin`
> **零命中** —— 代码里没有方向控制 GPIO，说明**方向切换由硬件自动方向电路完成**，
> 这部分电路在 HAT 板上。

### ⚠️ Armbian 的坑：UART2 默认跑着登录控制台

> `robotd-design.md` §原文：Armbian 默认在 UART2 上跑 `serial-getty@ttyS2`，
> `agetty` 会占着串口。必须 `systemctl mask serial-getty@ttyS2`。
> 官方是用 `fuser -v /dev/ttyS2` 查出来是 `agetty` 干的。

### 其余接口一览

| 接口 | 用途 | 参数 |
|---|---|---|
| **UART2 (ttyS2)** | 舵机 + IMU 板 | 1 Mbps TTL 半双工 |
| **I2C3 (M0，pin 3/5)** | 音频 codec / ToF /（未用的 BMI088） | 400 kHz |
| **I2S3 (i2s3_2ch)** | 音频数据 | MCLK 12 MHz，sysclk 12.288 MHz |
| **MIPI CSI** | IMX219 摄像头 | I2C 控制地址 0x10 |
| **蓝牙** | 手柄（`padd`）、手机 App（`btd`） | Radxa Zero 3W 板载 |
| **WiFi** | WebRTC 视频、配网（`configd`） | 板载 |
| **USB-C** | 供电 + maskrom 刷机 | PD 协商被 overlay 牺牲掉了 |
| **Unix socket** | 各守护进程间 JSON-RPC | 不是硬件 |

## 五之三、为什么必须用 Linux SoC，不能用 STM32 / ESP32

主控要同时干这些事：

| 任务 | 负载 |
|---|---|
| ONNX Runtime 跑策略 | `obs[1,61] → act[1,14]` @ **50 Hz** |
| WebRTC 视频推流 | 720p30 H.264，**Rockchip MPP 硬件编码** |
| RKNN NPU 目标检测 | `duck_detect.rknn`，2 Hz（**热限制**，满速 95°C） |
| GStreamer 管线 + 拥塞控制 | `rtpgccbwe` 占 7.6% 一个核 |
| 蓝牙手柄 + 手机 App + WiFi | BlueZ 协议栈 |
| 签名固件更新 / 回滚 | `updaterd` |

**MCU 做不了这些** —— 光是 WebRTC + H.264 硬编 + ONNX 推理就必须 Linux + 硬件编码器 + NPU。

所以选型是：**RK3566 四核 Cortex-A55 + Mali-G52 + NPU，跑 Armbian**。

> 📌 但注意：**原型阶段用的是树莓派 Zero 2W**。
> `robotd.toml` 注释原文：50 Hz 控制环 *"is inherited from the prototype, where it was
> chosen on a Raspberry Pi Zero 2W. It has never been re-derived on the Radxa."*
> Open Duck Mini v2 至今仍在用树莓派 Zero 2W —— 因为它不做视觉和 WebRTC。

### 那 `imu_to_dxl` 板上是什么 MCU？

**仓库里没有** —— 那是板子自己的固件，不在这个开源仓库里。
但从它要干的活可以反推需求：

- 做 **Dynamixel Protocol V2 从机**（响应 `sync_read`，ID 200，寄存器 124）
- 读 **LSM6DSV16X**（SPI 或 I2C）
- **1 Mbps UART** + 半双工方向切换
- 把 SFLP 四元数打包成 fp16

**STM32G0 / STM32G4 / CH32V203 / ESP32 都够用。** 这块正好是可以自由选型的地方 ——
只要在总线上表现得像个 Dynamixel 从机，主控不关心里面是什么芯片。

## 六、电源与电池

| 项目 | 值 |
|---|---|
| 电池 | **索尼 NP-F550 / NP-F970**（L 系列摄像机电池），**2S 锂离子** |
| 标称 | 7.2 V |
| 满电（负载下） | **8.2 V** |
| 空（负载下） | **6.6 V** |
| 电量计 | **无** |
| ADC | **无** |

### 电压怎么测的

> 注释原文：*"There is no fuel gauge and no ADC. The only measurement available is
> what the servos report as their own supply."*

**直接通过 Dynamixel 协议读舵机报告的自身供电电压**，即"从总线上看到的电池"。
所以这个值**会随负载下沉、静止时回升** —— 6.6~8.2V 这个区间是
**「带载可用区间」**，不是电芯化学量程。

电池 EMA（约 10 秒时间常数）跌到 6.6V → **自动优雅坐下并关机**。

> 这个设计对复刻很友好：**你不需要设计任何电池监测电路**。

## 八、软件侧关键参数（复刻时必须对齐）

| 参数 | 值 | 说明 |
|---|---|---|
| 控制环 | **50 Hz** | 继承自原型（树莓派 Zero 2W 上定的），在 Radxa 上**从未重新验证过** |
| 策略接口 | `obs[1,61] → actions[1,14]` | 加载时校验，51 维旧版会被拒绝 |
| `action_scale` | 0.9（走）/ 0.8（轮滑） | |
| 位置 P 增益 | **200** | 站立时 ×0.8 |
| 动作低通 | head **0.5** / legs **0.7** | **必须与训练时一致**，否则迁移性能下降 |
| 电压自适应 | 默认关 | 开启后 `scale × (7.4 / 实测EMA)`，钳位 6.0–9.5 V |

### 值得抄的两个工程细节

**1. 预测性软着陆（`limp_fall`）**

不是等摔倒了才反应，而是**外推**：投影重力随躯干旋转，其变化率正好是
`-(ω × g)`，用同一个 12 字节 IMU 块里的陀螺数据外推 **300 ms**。
当机器人**已经**倾斜超过约 26°、**且仍在继续倒**、且外推落点越过阈值 →
立刻把增益从 200 降到 **50**，让关节顺着外力走，**软着陆**。
停稳后（用陀螺判断静止，不是定时）再用 600ms 把姿态拉回站姿，
最后才交还给站立策略。

> 理由写得很好：站立策略「很会站起来，很不会摔倒」——
> 从静止的俯卧/仰卧能干净地起身，但从动态摔倒中它会反复尝试并失败，
> 用走路的增益跟地板较劲，电机为每一次尝试买单。

**2. NPU 检测的 2 Hz 是热限制**

> 注释原文：*"2 is a thermal limit, not a preference"* —— 满速跑会到 **95°C**，
> CPU 降频到 **408 MHz**，那就成了「为了看得清而走不好」的机器人。

## 九、自己复刻这套电控要做什么

### ✅ 直接买现成的

| 部件 | 型号 | 备注 |
|---|---|---|
| 主控 | **Radxa Zero 3W** | 市售模块，**不是定制板** |
| 舵机 | Dynamixel XL330 × 15 | |
| 电池 | 索尼 NP-F550 / F970 + 卡座 | 通用摄像机电池，配件遍地 |
| 摄像头 | 树莓派 Camera v2（IMX219） | |
| ToF | VL53L8CX 模块（Stemma/Qwiic） | |

### 🔧 需要自己画的两块板

**① `imu_to_dxl`（简单，强烈建议自己做）**
LSM6DSV16X + 小 MCU（Dynamixel V2 从机）+ 半双工 TTL 收发器。
协议和寄存器布局本文已完整给出，照着实现即可。

**② RPI Robot HAT（可以简化）**
原版 = TLV320AIC3104 + BMI088（没用）+ Stemma 接口 + 电源。
**复刻时可以砍掉 BMI088**，甚至整块板都可以用现成模块替代：
- 音频：任意 I2S codec 模块（或直接用 MAX98357A 功放，放弃录音）
- ToF：VL53L8CX 现成模块直接挂 i2c3
- 电源：现成 5V UBEC

> 也就是说，**如果你不要录音和喇叭，HAT 这块板可以完全不做**。

### ⚠️ 必须注意的坑

1. **i2c3 与 FUSB302 冲突** —— 用 pin 3/5 的硬件 I2C 就会失去 USB-C PD 协商
   （但普通 5V 充电仍可用）。见第四节。
2. **NPU 默认关闭** —— Armbian 出厂不开，要跑 rknn 模型得刷 overlay 并重启。
3. **摄像头是倒装的** —— 软件里要 `rotation=180`，用硬件编码器做，别用
   `videoflip`（那是对每一帧做全 CPU 遍历）。
4. **控制环 50 Hz 在 Radxa 上没验证过** —— 官方自己承认是从树莓派 Zero 2W
   继承来的数字。

## 十、结论：这套电控是可以复刻的

我此前判断「RK3566 定制载板买不到，PCB 是硬墙」——**这个判断需要修正**：

- 主控是**市售的 Radxa Zero 3W**，不是定制载板
- 两块自制板中，`imu_to_dxl` 元件极少、协议已完整还原，容易做
- HAT 板可以用现成模块替代，甚至在不要音频的情况下完全省略

**真正剩下的门槛是软件**：Rust 运行时虽然开源（Apache-2.0），但绑定
