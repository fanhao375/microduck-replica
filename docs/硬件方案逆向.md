# Microduck 硬件方案逆向

**简体中文** · [English](hardware-teardown.en.md)

**方法**：官方开源了 Rust 运行时，而运行时要驱动真实硬件，就必须写死设备路径、
I2C 地址、寄存器偏移、波特率和协议。**代码即规格书**。
本文所有结论都来自 `pollen-robotics/microduck` 仓库的源码、设备树和配置文件。

---

## 一、整体架构

```
                    ┌──────────────────────────────┐
                    │   Radxa Zero 3W (RK3566)     │  65 × 30 mm
                    │   Armbian / 内核 6.1.115      │  Pi Zero 形态
                    └──┬────────┬─────────┬────────┘
          /dev/ttyS2   │        │ 40-pin  │ MIPI CSI
          1 Mbps UART  │        │         │
        ┌──────────────┘        │         └── IMX219 摄像头（倒装）
        │                       │
        │              ┌────────▼─────────────────┐
        │              │  Pollen RPI Robot HAT    │  65×30mm 自制板(已开源)
        │              │  i2c3 @ 400kHz           │
        │              │   ├ TLV320AIC3104  0x18  │ 音频 codec
        │              │   ├ BMI088   0x19/0x68   │ 焊了但没用
        │              │   └ Stemma J5 → ToF 0x29 │
        │              │  电池经此板供电            │
        │              └──────────────────────────┘
        │
   ═════╪═══════════ Dynamixel 总线 (Protocol V2, 1 Mbps) ═══════════
        │
        ├── 15 × Dynamixel XL330    ID: 左腿20-24 / 颈头嘴30-34 / 右腿10-14
        └── imu_to_dxl v2 板         ID: 200      ← 第二块自制板
              └ LSM6DSV16X
```

**核心设计思想**：**一条 Dynamixel 总线搞定一切**。IMU 不走 I2C，而是做成 Dynamixel
从机挂在舵机总线上，和舵机在**同一次 `sync_read` 事务**里被读出来。
电池电压也不用电量计——直接读舵机报告的自身供电电压。

## 三、`imu_to_dxl` v2 —— 唯一需要自己画的板

**最巧妙的设计，也是最容易自己复刻的一块。**

| 项目 | 值 |
|---|---|
| IMU 芯片 | **LSM6DSV16X**（ST 6 轴，带 SFLP 硬件传感器融合块） |
| 接口 | **Dynamixel 总线**（不是 I2C！） |
| 总线 ID | **200** |
| 寄存器地址 | **124** |
| 控制环读取 | 12 字节 |
| 完整诊断块 | 20 字节（另含原始加速度、采样计数、状态标志） |

### 12 字节块布局

| 字节 | 内容 |
|---|---|
| `0..6` | gyro x/y/z，`i16` 小端原始计数，量程 **±500 dps**，**17.5 mdps/LSB** |
| `6..12` | SFLP 四元数 x/y/z，**IEEE 半精度 (fp16)**；`w = √(1 − x² − y² − z²)` |

### 为什么这么设计

1. **不占用额外总线** —— 和 15 个舵机在同一次 `sync_read` 里读回，零额外开销
2. **主机不用跑姿态融合** —— LSM6DSV16X 的 SFLP 块在芯片内直接输出游戏旋转四元数，
   还自己估计陀螺零偏
3. **只传 w 的三个分量** —— 单位四元数省一个字节对，12 字节刚好塞进一次事务

### 自己做这块板要什么

- LSM6DSV16X（或引脚兼容的 ST 6 轴）
- 一颗小 MCU 做 Dynamixel Protocol V2 从机（STM32G0 / CH32V 之类足够）
- 半双工 TTL 收发器（Dynamixel 总线是单线半双工）
- 供电从总线取

**这是整个项目里最值得自己画的一块板**，元件少、逻辑清晰、协议公开。

## 四、Pollen RPI Robot HAT —— **官方已开源，不必自己画**

> 📌 **勘误（2026-09-03）**：本节此前按「未开源、需逆向」处理。**这是错的。**
> 这块板在 [`pollen-robotics/elec_RPI_Robot_HAT`](https://github.com/pollen-robotics/elec_RPI_Robot_HAT)
> 有完整开源工程（**Apache-2.0**）：KiCad 9 原理图与 PCB、Gerber、BOM、贴片坐标、STEP、
> 以及全部器件手册。当时只检索了 `microduck` 主仓，漏掉了同组织下 `elec_` 前缀的硬件仓库。

**结论：这块板直接下载官方 Gerber 打样即可，本节保留作为「逆向 vs 实物」的对照记录。**

### ⚠️ 打样前必读的四件事

**1. 这块板没有充电电路，也没有 USB-C 输入。**

仓库里有张 `pwr_supply_charge.kicad_sch`，很容易让人以为板上带充电。**它是孤儿图纸** ——
`main.kicad_sch` 只实例化了 `audio / dynamixel / power / sensors` 四张子图，没有挂它；
图纸标题栏写的还是别的项目（`Chromapi's Power Supply & Charge`）。

生产 BOM 实测核对：`CN3302`（锂电充电 IC）、`HY2120`（保护）、USB-C 母座、
电源开关、指示 LED、`AO4435`/`FDS6630A` —— **一个都没有**。

板上真实存在的电源器件只有两颗：

| 位号 | 器件 | 作用 |
|---|---|---|
| `U10` | **LM5050-1** | 理想二极管控制器（防反接 / OR-ing） |
| `U9` | **AP63205** | 降压变换器 |

> **结论：电池必须用外部充电器充。** 插 USB-C 不会给机器人充电。

**2. 打开 KiCad 工程需要另一个仓库。**

HAT 仓库里**没有** `sym-lib-table`、`fp-lib-table` 或任何 `.pretty` 目录，
但原理图引用了 `Library_Pollen`、`LCSC_parts_lib`、`Lib_Pollen`。这些在
[`pollen-robotics/lib_KiCAD`](https://github.com/pollen-robotics/lib_KiCAD) 里
（`Symbols/Library_Pollen.kicad_sym`、`Footprints/Lib_Pollen.pretty`、`LCSC_parts/`）。

不装它直接打开，会是一片未解析的符号。
**只想打样的话不需要** —— 直接用 `production/` 里的 Gerber。

**3. 四层板，118 个贴片位，必须走 SMT 服务。**

`kicad_pcb` 的层定义是 `F.Cu / In1.Cu / In2.Cu / B.Cu`。BOM 47 行 123 颗元件，
含 **VQFN-32 的 codec** 和 **LGA-16 的 BMI088** —— 手焊不现实，下单时直接选贴片。

DNP（不贴）共 5 行：`C25`、`R10/R11`、`R16/R17/R41`、`R36/R37`、以及 **`U4`**。

**4. `U4 = CAT24C32` 不贴 → 这不是自识别 HAT。**

EEPROM 位置空着，所以它不符合 `hat-plus-specification` 的自动探测流程，
系统不会自动认出这块板。设备树 overlay 得手动配。

### 补充：Dynamixel 侧其实是双制式

| 位号 | 接口 | 说明 |
|---|---|---|
| `J13 / J14` | **TTL 3P**（JST EH 2.5mm） | Microduck 的 XL330 走这路 |
| `J3 / J11` | **RS-485 4P**（JST EH 2.5mm） | 由 `U8 = SIT3088E` 驱动 |
| `TH1` | 100R 热敏电阻 | 过流保护 |

也就是说这块板**同时能驱动 TTL 和 485 两种 Dynamixel，以及飞特舵机**（换线即可）。

### 补充：它不是 Microduck 专用板

这是一块「小/中型机器人通用 HAT」，已知三个使用者：

- **Microduck**（本项目）
- Pollen 自家的 **Grabette / Casquette**（跑在 Pi 4 上）
- 第三方 **[`Rhoban/microban`](https://github.com/Rhoban/microban)** —— 19×XL330 + Pi Zero 2W + 2×18650 的双足机器人，
  **有一份完整公开的 BOM + 装配 + 打印指南**（整机约 $567），采购时值得对照

> `Rhoban/microban` 的 BOM 里对这块板的描述值得记住：
> *"与其他元件不同，RPI Robot Hat 不是现成货：这是一块开源板，你需要自己送厂制造。"*
> —— **开源 ≠ 买得到**，还是得打样。

### 逆向结论与官方 BOM 的比对

| 本文逆向推出 | 官方 BOM 实际 | 结果 |
|---|---|---|
| 音频 codec @ `0x18` | `U2 = TLV320AIC3104IRHBR` | ✅ |
| BMI088 @ `0x19/0x68`，焊了没用 | `U11 = BMI088` | ✅ |
| 上拉「单对 10k，**R12/R13**」 | `R12, R13 = 10k` | ✅ **位号完全命中** |
| 「Stemma **J5** 接口」 | `J5–J8 = JST SH 1mm 4P` | ✅ |
| Pi Zero 形态 40 针 | `J4 = 2x20 rasp HAT zero SMD` | ✅ |

### 逆向时**没能看出来**的部分（源码里不体现）

| 器件 | 作用 |
|---|---|
| `U1 = PAM8406D` | D 类音频功放 |
| `MK1 = LMA2718` | **板载 MEMS 麦克风** |
| `U10 = LM5050-1` | 理想二极管控制器（防反接 / OR-ing） |
| `AP63205` | 降压变换器 |
| `CAT24C32` | EEPROM —— Raspberry Pi HAT+ 规范要求的身份识别 |
| `J1/J2/J9 = Wago-2` | 免螺丝端子：外接喇叭、第二个麦克风 |
| `J3/J11`、`J13/J14` | Dynamixel 4P / 3P 连接器（JST EH 2.5mm） |

官方 README 还给出了两条源码里读不到的信息：

- **供电范围 5–28 V**，设计上就是**从电机接口取电**
- Dynamixel **TTL 与 RS485 都支持**（换线即可，也能驱动飞特舵机）

### 板载器件

| 器件 | I2C 地址 | 说明 |
|---|---|---|
| **TLV320AIC3104** | `0x18` | TI 音频 codec，I2S 数据 + I2C 控制 |
| **BMI088** | `0x19` / `0x68` | **真的贴了片但软件不用**（BOM `U11`；注释原文 "dormant"、"unused but still connected"）。外界说 Microduck「有两颗 IMU」指的就是它 |
| **ToF** | `0x29` 或 `0x52` | 不在板上，通过 **Stemma/Qwiic J5** 外接。固件**同时支持 VL53L5CX 和 VL53L8CX**，按 revision ID 自动识别 |

- I2C 总线：40 针的 **pin 3 / pin 5**（`GPIO1_A0` = SDA，`GPIO1_A1` = SCL）
- 总线速率 **400 kHz**（受限于 codec 和 BMI088；VL53L5CX 本可以跑 1 MHz）
- 上拉：**单对 10k，R12/R13**
- 音频时钟：MCLK **12 MHz** 固定晶振，I2S sysclk **12.288 MHz**（256 × 48kHz）
- **机器人内部供电经此板**（电池 → HAT → 主控）

### ⚠️ 一个他们自己踩过的坑（注释里写得很清楚）

RK3566 的 `i2c3` 控制器在原厂 DTB 里跑在 **M1 pinmux**（`GPIO3_B5/B6`，靠近 USB-C 口），
服务 **FUSB302 USB-C PD 控制器**。而 HAT 要用的 pin 3/5 正好是 `i2c3` 的 **M0 pinmux**。

他们的 overlay 把控制器重新 mux 到 M0，并禁用 fusb302 节点。后果：

- **失去 USB-C PD 协商**
- 但 FUSB302 上电默认在两条 CC 线上呈现 Rd（`SWITCHES0 = PDWN1|PDWN2`），
  所以 USB-C 充电器（无论 PD 还是普通）**仍然给 5V** —— 板子本来就只要 5V
- 机器人内部供电走电池经 HAT，与此无关
- maskrom 刷机是 ROM code，不受影响

> 早期版本用的是 **bit-bang I2C**（`i2c-gpio-pihat`），CPU 占用高。
> 改成硬件 I2C 后才让 **15 Hz 的 ToF 流**变得可负担。
> 两种模式互斥，`install.sh` 通过 `MICRODUCK_I2C_MODE=hw|bitbang` 选择。

### 稳定设备节点

`/dev/i2c-3` 通过 udev 规则软链为 **`/dev/i2c-pihat`**，两种模式下消费者代码不用改。

## 五之二、通讯方案（逐条确认）

### 主总线：单线半双工 TTL UART —— **不是 RS232，也不是 RS485**

| 项目 | 值 | 依据 |
|---|---|---|
| 电气层 | **3 线 TTL 半双工**（数据线 + VDD + GND） | XL330 产品规格：3-pin JST，TTL |
| 逻辑电平 | **3.3 V** | RK3566 IO 电平 |
| 协议 | **Dynamixel Protocol V2** | `.with_protocol_v2()` |
| 速率 | **1 Mbps** | `BAUD_RATE = 1_000_000`，EEPROM 寄存器 `baud_rate = 3` |
| 端口 | `/dev/ttyS2` = RK3566 **UART2，M0 pinmux** | `robotd.toml`，`uart2-m0` overlay |
| 挂载设备 | **16 个**：15 舵机 + 1 块 IMU 板 | `ids = [200, 20..24, 30..34, 10..14]` |
| 单次事务 | 一个 `sync_read` 覆盖全部 16 个设备，寄存器 **124–136** | `bus.rs` |

> ❗ **不是 RS485**。RS485 是差分双线，Dynamixel 的 XM/XH 系列才用（4-pin）。
> XL330 是 **TTL 单线半双工**（3-pin）。全仓库搜 `rs485|rs232|half-duplex|direction pin`
> **零命中** —— 代码里没有方向控制 GPIO，说明**方向切换由硬件自动方向电路完成**，
> 这部分电路在 HAT 板上。

### ⚠️ Armbian 的坑：UART2 默认跑着登录控制台

> `robotd-design.md` §原文：Armbian 默认在 UART2 上跑 `serial-getty@ttyS2`，
> `agetty` 会占着串口。必须 `systemctl mask serial-getty@ttyS2`。
> 官方是用 `fuser -v /dev/ttyS2` 查出来是 `agetty` 干的。

### 其余接口一览

| 接口 | 用途 | 参数 |
|---|---|---|
| **UART2 (ttyS2)** | 舵机 + IMU 板 | 1 Mbps TTL 半双工 |
| **I2C3 (M0，pin 3/5)** | 音频 codec / ToF /（未用的 BMI088） | 400 kHz |
| **I2S3 (i2s3_2ch)** | 音频数据 | MCLK 12 MHz，sysclk 12.288 MHz |
| **MIPI CSI** | IMX219 摄像头 | I2C 控制地址 0x10 |
| **蓝牙** | 手柄（`padd`）、手机 App（`btd`） | Radxa Zero 3W 板载 |
| **WiFi** | WebRTC 视频、配网（`configd`） | 板载 |
| **USB-C** | 供电 + maskrom 刷机 | PD 协商被 overlay 牺牲掉了 |
| **Unix socket** | 各守护进程间 JSON-RPC | 不是硬件 |

## 五之三、为什么必须用 Linux SoC，不能用 STM32 / ESP32

主控要同时干这些事：

| 任务 | 负载 |
|---|---|
| ONNX Runtime 跑策略 | `obs[1,61] → act[1,14]` @ **50 Hz** |
| WebRTC 视频推流 | 720p30 H.264，**Rockchip MPP 硬件编码** |
| RKNN NPU 目标检测 | `duck_detect.rknn`，2 Hz（**热限制**，满速 95°C） |
| GStreamer 管线 + 拥塞控制 | `rtpgccbwe` 占 7.6% 一个核 |
| 蓝牙手柄 + 手机 App + WiFi | BlueZ 协议栈 |
| 签名固件更新 / 回滚 | `updaterd` |

**MCU 做不了这些** —— 光是 WebRTC + H.264 硬编 + ONNX 推理就必须 Linux + 硬件编码器 + NPU。

所以选型是：**RK3566 四核 Cortex-A55 + Mali-G52 + NPU，跑 Armbian**。

> 📌 但注意：**原型阶段用的是树莓派 Zero 2W**。
> `robotd.toml` 注释原文：50 Hz 控制环 *"is inherited from the prototype, where it was
> chosen on a Raspberry Pi Zero 2W. It has never been re-derived on the Radxa."*
> Open Duck Mini v2 至今仍在用树莓派 Zero 2W —— 因为它不做视觉和 WebRTC。

### 那 `imu_to_dxl` 板上是什么 MCU？

**仓库里没有** —— 那是板子自己的固件，不在这个开源仓库里。
但从它要干的活可以反推需求：

- 做 **Dynamixel Protocol V2 从机**（响应 `sync_read`，ID 200，寄存器 124）
- 读 **LSM6DSV16X**（SPI 或 I2C）
- **1 Mbps UART** + 半双工方向切换
- 把 SFLP 四元数打包成 fp16

**STM32G0 / STM32G4 / CH32V203 / ESP32 都够用。** 这块正好是可以自由选型的地方 ——
只要在总线上表现得像个 Dynamixel 从机，主控不关心里面是什么芯片。

## 六、电源与电池

| 项目 | 值 |
|---|---|
| 电池 | **索尼 NP-F550 / NP-F970**（L 系列摄像机电池），**2S 锂离子** |
| 标称 | 7.2 V |
| 满电（负载下） | **8.2 V** |
| 空（负载下） | **6.6 V** |
| 电量计 | **无** |
| ADC | **无** |

### 电压怎么测的

> 注释原文：*"There is no fuel gauge and no ADC. The only measurement available is
> what the servos report as their own supply."*

**直接通过 Dynamixel 协议读舵机报告的自身供电电压**，即"从总线上看到的电池"。
所以这个值**会随负载下沉、静止时回升** —— 6.6~8.2V 这个区间是
**「带载可用区间」**，不是电芯化学量程。

电池 EMA（约 10 秒时间常数）跌到 6.6V → **自动优雅坐下并关机**。

> 这个设计对复刻很友好：**你不需要设计任何电池监测电路**。

## 七、传感器

### ToF 深度

## 七之二、NPU 与板载视觉推理

> 本节据上游 `docs/project/npu-bringup.md` 与 `duck-detect/` 整理。
> 这是目前唯一一份把「RK3566 的 NPU 到底能干什么」写实的材料。

### NPU 规格

| 项目 | 值 | 来源 |
|---|---|---|
| 算力 | **0.8 TOPS，INT8，单核** | `npu-bringup.md` 开篇 |
| 设备树节点 | `npu@fde40000` | Armbian 出厂 `status = "disabled"` |
| 运行时 | rknn-toolkit2 运行时 `librknnrt.so` | 驱动 0.9.8 / 运行时 2.3.2（实测） |

### ⚠️ 两条会卡死复刻的硬约束

**1. 驱动只存在于厂商内核，mainline 没有。**

> 原文：*"The driver is the gate: it is part of the vendor kernel, mainline has none,
> and nothing in userspace can work around its absence."*

这条比「NPU 默认关闭」严重得多。换成主线内核的发行版（大部分 Debian/Ubuntu 官方镜像），
**NPU 直接没有，用户态无解**。复刻时系统镜像不能随便换。

**2. Armbian 在每一块 Radxa Zero 3 上都把 NPU 节点关着。**

所以一块「原厂」板子是：硬件有、内核有、驱动有，**但没有 NPU**。

```bash
# 上游做法：随 robotctl update 的 preinstall hook 自动跑，失败不致命
sudo sh /opt/robot/daemon/current/scripts/setup-npu.sh
# 写 overlay → 必须重启 → 确认：
dmesg | grep rknpu
```

脚本要跑**发布包里那一份**，不能跑 `/usr/local/sbin/robot-setup-npu` ——
overlay 源文件和脚本放在一起，单独那份首次运行时旁边什么都没有。

### 鸭子检测器

模型训练在**另一个独立仓库** [`pollen-robotics/duck_detector`](https://github.com/pollen-robotics/duck_detector)，
到这边时已经是量化好的 `.rknn`。

| 项目 | 值 |
|---|---|
| 网络 | `yolo11n` @ **320×320** |
| 类别 | **1 类**（就是鸭子） |
| 训练集 | **3 个 session 共 150 帧** |
| mAP50 | **0.976**（留出 session 上） |
| INT8 量化后体积 | **3.9 MB** |
| 量化损失 | 桌面实测 2/2 检出，框重叠 95%（对比 float 模型） |

> 150 帧就能到 0.976 —— 单类别、固定目标、场景受限，这个量级的数据要求
> 对复刻者是好消息。

### 实测性能（Radxa Zero 3，2 Hz 节流，30 帧 × 3 轮）

| 项目 | 实测 | 说明 |
|---|---|---|
| 延迟 p50 / p95 | **25.7 ms / 58.4 ms** | 推理 + 解码，不含 JPEG 解码 |
| 每帧 CPU | 20.7 ms | **注意：这不是 NPU 的开销**，见下 |
| SoC 温度 | **63 °C** | 节流跑完时 |

**那个 CPU 数字很容易被误读。** 延迟列算的是 `infer` + `decode`；
CPU 列是整个循环的进程 CPU 除以帧数，因此**还包含 `letterbox_rgb`**——
一次 1280×720 → 320×320 的重采样，跑在 CPU 上，且完全不在延迟列里。
剩下的部分是不是 `rknn_run` 忙等（把 NPU 等待算到 CPU 头上），上游自己也还没测清楚。

> 2 Hz 下无论如何都只是**单核的 4%**。但在引用「感知的代价」之前，这两块得分开测。

关于 2 Hz 为什么是 2 Hz，见 [§八 值得抄的两个工程细节](#值得抄的两个工程细节)——
那是**热限制不是偏好**，满速会到 95 °C。

### 三个工程决策值得抄

**1. `dlopen` 而不是链接。** `librknnrt.so` 是厂商 blob，不在任何 Debian 源里；
一旦链接它，CI 里就没法交叉编译。代价是多写一个 `duck-detect/src/rknn.rs`，
好处是 `cargo board --bins` 在笔记本上照样能跑。`robotd` 加载 ONNX Runtime 用的是同一套办法。

**2. 让运行时做反量化。** 量化模型的输出张量是 int8 + scale + zero point。
`rknn_outputs_get` 可以直接转成 float，上游选择让它转 ——
另一条路是把 scale 带进解码器，**总有一天会悄悄算错一次**。

**3. 排查顺序是「能不能跑 → 还认不认得出 → 花多少钱」。**
`duck-bench` 就是按这个顺序报的。一个能跑但检不出任何东西的模型，
看起来和正常的一模一样。

> ⚠️ **量化模型的分数是另一套刻度。** float 模型的 0.5 不是这个模型的 0.5。
> 检不出东西时，先把 `--threshold` 调到 **0.2** 再怀疑转换坏了。

### 目前还缺什么

**机器人上没有任何东西能拿到一帧图像。** `mediad` 里有一条专为此存在的
raw NV12 tee 分支，但**没有 IPC 暴露它** —— 这也是为什么采集数据集必须先停掉 `mediad`
才能抢到摄像头。

上游给了两条路（不互斥）：一是加 `media.frame` 调用，返回单帧；
二是把检测器搬进 `mediad`，订阅 raw 分支、几 Hz 跑一次、把检测结果发到状态流上。

> 第二条是终局形态：**感知放在传感器旁边，输出特征而不是搬像素**。

### 对复刻者的结论

1. **系统镜像不能随便换** —— 必须是带 Rockchip 厂商内核的（Armbian 系）
2. 拿到板子第一件事是**开 NPU 节点并重启**，否则一切推理都在 CPU 上
3. 想自己训模型，**150 帧起步**就有可用精度，门槛比想象中低
4. 别指望现在就能从机器人上取帧做二次开发 —— **这条链路上游自己还没打通**

## 八、软件侧关键参数（复刻时必须对齐）

| 参数 | 值 | 说明 |
|---|---|---|
| 控制环 | **50 Hz** | 继承自原型（树莓派 Zero 2W 上定的），在 Radxa 上**从未重新验证过** |
| 策略接口 | `obs[1,61] → actions[1,14]` | 加载时校验，51 维旧版会被拒绝 |
| `action_scale` | 0.9（走）/ 0.8（轮滑） | |
| 位置 P 增益 | **200** | 站立时 ×0.8 |
| 动作低通 | head **0.5** / legs **0.7** | **必须与训练时一致**，否则迁移性能下降 |
| 电压自适应 | 默认关 | 开启后 `scale × (7.4 / 实测EMA)`，钳位 6.0–9.5 V |

### 值得抄的两个工程细节

**1. 预测性软着陆（`limp_fall`）**

不是等摔倒了才反应，而是**外推**：投影重力随躯干旋转，其变化率正好是
`-(ω × g)`，用同一个 12 字节 IMU 块里的陀螺数据外推 **300 ms**。
当机器人**已经**倾斜超过约 26°、**且仍在继续倒**、且外推落点越过阈值 →
立刻把增益从 200 降到 **50**，让关节顺着外力走，**软着陆**。
停稳后（用陀螺判断静止，不是定时）再用 600ms 把姿态拉回站姿，
最后才交还给站立策略。

> 理由写得很好：站立策略「很会站起来，很不会摔倒」——
> 从静止的俯卧/仰卧能干净地起身，但从动态摔倒中它会反复尝试并失败，
> 用走路的增益跟地板较劲，电机为每一次尝试买单。

**2. NPU 检测的 2 Hz 是热限制**

> 注释原文：*"2 is a thermal limit, not a preference"* —— 满速跑会到 **95°C**，
> CPU 降频到 **408 MHz**，那就成了「为了看得清而走不好」的机器人。

## 九、自己复刻这套电控要做什么

### ✅ 直接买现成的

| 部件 | 型号 | 备注 |
|---|---|---|
| 主控 | **Radxa Zero 3W** | 市售模块，**不是定制板** |
| 舵机 | Dynamixel XL330 × 15 | |
| 电池 | 索尼 NP-F550 / F970 + 卡座 | 通用摄像机电池，配件遍地 |
| 摄像头 | 树莓派 Camera v2（IMX219） | |
| ToF | VL53L8CX 模块（Stemma/Qwiic） | |

### 📥 直接下载官方工程的一块板

**RPI Robot HAT —— 不用画。**
[`pollen-robotics/elec_RPI_Robot_HAT`](https://github.com/pollen-robotics/elec_RPI_Robot_HAT)（Apache-2.0）
里有 `production/` 目录，Gerber、BOM、贴片坐标齐全，直接下单打样贴片即可。

若想简化（不要录音和喇叭），也可以整块不做：ToF 模块直接挂 i2c3、电源用现成 5V UBEC。

### 🔧 唯一需要自己画的板

**`imu_to_dxl`** —— 全网无公开工程，这是**唯一必须自己重建**的一块。
LSM6DSV16X + 小 MCU（Dynamixel V2 从机）+ 半双工 TTL 收发器。
协议和 12 字节寄存器布局本文已完整给出，照着实现即可。

### ⚠️ 必须注意的坑

1. **i2c3 与 FUSB302 冲突** —— 用 pin 3/5 的硬件 I2C 就会失去 USB-C PD 协商
   （但普通 5V 充电仍可用）。见第四节。
2. **NPU 默认关闭** —— Armbian 出厂不开，要跑 rknn 模型得刷 overlay 并重启。
3. **摄像头是倒装的** —— 软件里要 `rotation=180`，用硬件编码器做，别用
   `videoflip`（那是对每一帧做全 CPU 遍历）。
4. **控制环 50 Hz 在 Radxa 上没验证过** —— 官方自己承认是从树莓派 Zero 2W
   继承来的数字。

## 十、结论：这套电控是可以复刻的

我此前判断「RK3566 定制载板买不到，PCB 是硬墙」——**这个判断需要修正**：

- 主控是**市售的 Radxa Zero 3W**，不是定制载板
- **HAT 板官方已完整开源**（KiCad + Gerber + BOM），根本不用画
- 剩下的 `imu_to_dxl` 元件极少、协议已完整还原，是唯一要自己做的一块

**真正剩下的门槛是软件**：Rust 运行时虽然开源（Apache-2.0），但绑定
Radxa Zero 3W 的具体接线；如果你照着同样的主控做，**运行时可以直接跑**。

> `tof/src/*.rs`、`mediad/src/*.rs`、`docs/project/media-bringup.md`。
